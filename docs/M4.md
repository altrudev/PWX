# M4 design: public log, revocation, key rotation and update policies

**Status: design approved by Altru on 2026-11-16, with the decisions at the end. Nothing here is built.** It closes audit item
M4 and is the foundation for lineage, blessings, ownership transfers and licenses
([`VISION.md`](VISION.md)).

## The problem in one line

Today, a publisher whose key is stolen can't be stopped: the thief can sign "updates" that every
loader accepts, nobody is told, and nothing can be taken back.

## The idea

Two layers:

1. **Make one stolen key useless.** Signing keys live in device hardware and can't be copied, and
   publishing needs **two of the author's devices**: one signs, another shows exactly what is
   being published and approves it. A thief with one device, or one copied file, can't publish.
2. **Make anything that slips through public and reversible.** Every important event goes into
   **one public, append-only log**, and loaders only trust what's in it. Anything signed is
   public, the author is alerted within minutes, the identity can't be taken over during a
   waiting period, and a bad release or key can be revoked.

Everything users see must be automatic: no manual checks, no key handling, no settings to
understand.

| Piece | What it stops |
| --- | --- |
| 0. Hardware keys and two-device approval | publishing with one stolen device or copied key |
| 1. Public log with witnesses | secret releases; a log showing different people different histories |
| 2. Receipts inside packages | needing the network to verify (offline still works) |
| 3. Publisher key history with a recovery key | a stolen key quietly replacing the real one |
| 4. Revocation | bad releases and stolen keys staying trusted |
| 5. Update policies | updates from anyone but the app's real publisher |
| 6. Monitors | a stolen key going unnoticed |

## 0. Signing: hardware keys and two-device approval

- **Keys that can't be copied.** Each of the author's devices makes its own signing key inside its
  security hardware (passkey-style platform keys, the secure enclave or TPM, or non-extractable
  browser keys where no hardware is available). Malware can ask the device to sign, but can't take
  the key away.
- **Two devices to publish.** A release needs signatures from two of the author's devices (for
  example laptop and phone). The approving device shows a plain summary of what is being signed:
  *"Publish Notes 1.3. New: camera access."* The author taps Approve or Deny. This is "what you see
  is what you sign": malware on the laptop can't change what the phone shows.
- **One author, many devices,** like Lullwire: every device the author adds runs the PWX Signer
  and gets its own key in the author's key history. Losing one device means removing it, not
  starting over.
- **Single-device authors** (a student's first app) may publish with one device. Loaders show
  those releases as "one-device signed", and their key history can be upgraded later.

## 1. The log

An append-only Merkle tree log, the same design browsers use for HTTPS certificates
(Certificate Transparency) and Sigstore uses for software releases.

- **Entries** are small signed records. Only fingerprints go in, never app contents or names of
  owners:

  | Entry | Contents |
  | --- | --- |
  | `release` | app id, version, manifest hash, publisher key id |
  | `loader-release` | PWX loader/runtime release hash and version |
  | `key-event` | publisher key created, rotated, or recovery key used |
  | `revoke` | a release, a version range, or a key from a point in time |
  | `lineage` | "this app branches from that one"; blessings (co-signatures) |
  | `transfer` | ownership or license moves from one key to another |

- **Format:** follow the public C2SP formats (signed-note checkpoints, tiled log). A tiled log is
  plain static files, so it can be served from ordinary hosting or a CDN, and mirrored by anyone.
- **The log can't forge anything.** Every entry is signed by its author. The worst a log
  operator can do is refuse or delay entries, which is visible.

## 2. Witnesses

In plain words: the log is a public notebook of every release, and someone has to host it. The
host, or anyone who breaks into the host, could show different people different pages and hide a
bad release from some of them ("split view").

**Witnesses** are independent notaries. Every few minutes each one checks that the notebook only
grew and was never changed, and stamps it. Loaders accept a page only if enough notaries stamped
it (for example 2 of 3), so cheating means fooling the host and two independent parties at once.

First witnesses: ALTRU on a second, separate host; a trusted partner; and existing public witness
networks or peers from the Agent Trust federation (to be asked).

## 3. Receipts: verification stays offline

When a release is logged, the publisher gets a **receipt**: the witnessed log state plus a short
proof that the release is in it. The receipt travels **inside the package**. A loader checks it
with no network at all, the same way it checks signatures today. This keeps PWX offline-first.

## 4. Publisher identity: key history and a recovery key

A publisher is not one key, but a **key history** that starts with a first `key-event` in the log.

- **Two keys from day one.** The everyday **signing key** signs releases. A **recovery key**
  stays offline (paper, USB stick, password manager). The first log entry records a fingerprint of
  the recovery key, so it can't be swapped later. (This "pre-commit to the next key" idea comes
  from KERI.)
- **Normal rotation:** the old signing key signs the new one. It's logged, and takes effect only
  after a **waiting period of 7 days**. The PWX Signer rotates keys **automatically** on a schedule
  and when a device is added or removed; the author does nothing. During the wait, loaders keep trusting the old
  key, and the publisher's monitor shouts.
- **Theft:** if a thief starts a rotation, the real publisher uses the recovery key to cancel it,
  revoke the stolen key and set a new one, **immediately**. Only the recovery key skips the wait.
- **Organisations** can require several keys to sign (for example 2 of 3), so no single stolen
  laptop can publish.

## 5. Revocation

- A publisher (signing or recovery key) can revoke a **release**, a **version range** or a **key
  from a point in time**. Releases signed before that point stay valid; later ones don't.
- **Loaders check privately.** Asking "is app X revoked?" would tell the server which apps you
  use. Instead, loaders download the **whole revocation list** (small, compressed) and check it
  on the device.
- **Automatic:** whenever a device is online, the shell fetches the revocation list in the
  background, about once a day. Users never see it.
- **Offline:** apps keep working. Only after **30 days** offline, and only for apps whose publisher
  had a key event in that time, does the shell ask to go online before opening them.

## 6. Update policies

Each manifest declares who may update it:

```json
"updates": { "publisher": "<key history id>", "minVersionStep": "patch" }
```

- A loader installs an update only if it's signed by a current key in **that** key history, is
  newer, is in the log, and isn't revoked. Branches are new apps with their own key history,
  linked by a `lineage` entry, never "updates" of the original.
- If an update asks for **more** capabilities (a new host, the camera), the user is asked again.
  Fewer or equal capabilities update silently.

## 7. Monitors

Anyone can watch the log. The PWX Signer watches the author's own key history on every device:
anything published, rotated or revoked under it raises an alert on all of them within minutes,
with one-tap **revoke**. Public monitors can also watch for patterns, like one key publishing hundreds of
apps.

## 8. The PWX Signer

A small app on each of the author's devices. It holds that device's key, approves releases from
the author's other devices, rotates keys, and watches the log.

- **It isn't an ordinary PWX app.** It ships as part of the PWX core, signed by the PWX release key
  and checked like the loader (audit M6). Apps run in sealed boxes and can't reach it or its keys
  (the C3 fix).
- **A virus can't rewrite it to steal keys:** the keys never leave the hardware, and every release
  still needs approval on another device that shows what is being signed.
- **Remaining risk:** an attacker controlling two of the author's devices at once, or an author
  approving without reading. The approval screen must be plain and short, and unusual requests
  (new permissions, a new device, a revoke) must stand out.

## What this changes in the threat table

| Threat | Before M4 | After M4 |
| --- | --- | --- |
| Stolen key or one stolen device | silent malicious updates, forever | can't publish: hardware keys can't be copied and a second device must approve |
| Author's devices both compromised, or author approves without reading | n/a | release is public, all devices alert, one-tap revoke; identity can't be taken over during the waiting period |
| Malicious host serves an old or different release | blocked by version rules only | also must be logged and unrevoked |
| Log operator cheats | n/a | needs the witnesses to collude; can't forge entries |
| User offline | trusted everything | still works, with a visible "last checked" date |

## Rollout

1. **Signer spike:** hardware-backed keys in each engine and platform, two-device approval over a
   paired channel, and the approval screen.
2. **Log spike:** a tiled log on the VPS, two witnesses, receipts in packages, the loader checking
   them. Tests: a release missing from the log, a forged receipt, a split view, a revoked release,
   a rotation inside the waiting period, a recovery-key cancel.
3. **Soft mode:** loaders verify receipts and warn when missing.
4. **Required mode:** loaders refuse unlogged releases (new installs first, then updates).
5. Then build lineage, blessings, transfers and licenses on the same log.

## Decisions (Altru, 2026-11-16)

1. **Design approved**, with a stronger defence against stolen keys: hardware keys plus two-device
   approval (section 0), not only detection after the fact.
2. **Waiting period** for key rotation: **7 days**.
3. **Painless:** revocation checks and key rotation are automatic. Users are asked only after
   30 days offline, and only for affected apps.
4. **First log** on ALTRU's static hosting, with at least two independent witnesses (to be asked).
5. **Recovery key:** both a printed QR code and a password-manager entry.
6. **PWX Signer** (section 8) on every author device, like Lullwire.
